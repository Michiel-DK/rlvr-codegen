Testing the Tests

Before teaching an AI to write code by rewarding it when the tests pass, we asked a harder question first: how often do the tests say "pass" when the code is actually wrong? Now we know. This page explains what we did and what we found — no jargon required.

The setup

Why "the tests pass" is a risky reward

A popular way to train coding AIs is simple: give the model a problem, run the problem's tests on its answer, and reward it when they go green. It feels objective. But an AI under training is a relentless optimizer — if there is any way to make the tests green without actually solving the problem, sooner or later it can find it. That failure mode has a name: reward hacking.

Most projects train first and worry about this later. We did it the other way around: measure how leaky the reward is before training anything against it.

What we did

Three measurements, two bonuses, zero dollars

  • 01

    Built the measuring rig

    A locked-down sandbox that runs untrusted code safely, plus a fixed, seeded setup so every number on this page can be regenerated with one command. We calibrated it first: the official correct solutions pass 100% — so when something fails later, it's the code, not the rig.

  • 02

    Tested the tests

    We took the official solutions to ~540 benchmark problems and planted 5,932 small bugs in them — a flipped comparison here, an off-by-one there. Then we checked: do the problem's own tests catch the bug? A much larger independent test set acted as the referee.

  • 03

    Probed the AI

    We had a small, untrained code model (running free on a laptop) write 1,610 solutions, and checked every one against both the normal tests and the larger referee set. The question: of the answers that look correct, how many actually aren't?

Two bonuses along the way: an exam of 39 real bugs mined from our own private repos (each one verified: the test genuinely fails before the fix and passes after), and a fact-checked written report of everything in the repository.

Of every 8 AI answers that pass the visible tests, roughly 1 is actually wrong — the tests just can't see it.

4–6% of planted bugs slip past the problems' own tests but are caught by the larger referee set — a measured blind spot in the reward
12–18% of the AI's "passing" answers are actually wrong — before any training has pushed it to game the tests
39 real tasks mined from our own repos, forming an exam no public model has ever seen
$0 spent — everything ran on a laptop; the GPU stays unrented until the numbers justify it
"Tests pass" overstates correctness — and now we know by how much, instead of guessing.

One more pattern worth noticing: the benchmark with fewer tests per problem leaked more on both measurements (6% vs 4% for planted bugs; 18% vs 12% for AI answers). Weaker tests, leakier reward — the direction theory predicted, now with numbers attached.

Why it matters

The "before" photo that makes training honest

If we later spend the ~$30–80 to actually train the model against this reward, we can re-measure one number on the same held-out problems: the share of "passing" answers that are secretly wrong. Today it's 12%. After training, it moves — and the direction tells the whole story:

If it goes up

The model learned to game the tests — reward hacking, measured directly instead of suspected.

If it goes down

The model genuinely got better at writing correct code — the reward taught the right thing.

Without this weekend's measurements, those two outcomes would be indistinguishable. That is the whole point of doing the boring part first.
